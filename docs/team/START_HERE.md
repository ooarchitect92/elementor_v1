Use the README setup commands. Run the foundation tests before changing a shared interface.
Create a personal feature branch from this base. Keep shared-contract/database PRs small and reviewable.

supplies handles. CODEOWNERS does not activate branch protection by itself.

## What is implemented now
Strict shared TypeScript contracts and emitted declarations; unit-tested permission/state/retry/cache/
message semantics; PostgreSQL transaction/job+outbox helper; separate schema with composite tenant keys
and RLS policies; local Docker topology; broker initialization and smoke scripts; a read-only WP plugin;
legacy request IDs/live-ready probes/graceful stop; no more import-time schema repair; CI and a full
36-package registry with explicit partial/planned states.

## What is not wired yet
No new production tenant authentication endpoints or backfill. No complete real Rabbit consumer loop,
Kafka projection service, Redis session cache, WordPress pairing, content import, renderer, CDN activation,
billing or capacity certification. Pure adapters use dependency injection; fake-client tests establish
contract behavior, not network/failover correctness. The default stack does not auto-consume jobs.

## Required contracts before parallel integration
1. API team owns trusted session+membership resolution; callers cannot grant themselves a tenant ID.
2. Save requests use expectedRevision and idempotencyKey; all existing JSON settings round-trip.
3. Job producer writes business change + job + outbox in one SQL transaction, then returns accepted.
4. Outbox destination acknowledgements are independent. Leases use DB time and unique fencing tokens.
5. An early consumer can see a broker task before a relay commits its SENT marker; claim logic must
   safely accept authoritative ACCEPTED/QUEUED jobs without losing that race.
6. Consumers never claim success on unsupported handlers. Reconcile expired/unknown work before retries.
7. Generated APIs must distinguish actual endpoints from planned schemas; no fake healthy integration UI.

## Frontend integration
Keep the existing visual language. Use job states for future timelines; use compatibility flags for WP UI.
Do not add a button that reports a successful pairing/import until its backend/permission/storage path
is tested. The baseline route/schema inventory is generated by `npm run inventory` and is heuristic,
not proof that each UI feature is mounted or correct. F01 owns the full route-to-function audit.
