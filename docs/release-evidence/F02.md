# F02 tenant membership — implementation evidence

Status: IN PROGRESS

## Implemented in this increment
- Server-side tenant membership resolution from `platform.memberships` using the authenticated session user's persisted UUID.
- Transaction-local `app.user_id` membership discovery with RLS; request body/header values are never used as user authority.
- `x-forgestudio-tenant` is treated only as a tenant selector and must resolve to an ACTIVE persisted membership for the authenticated user.
- Automatic selection is allowed only when the user has exactly one active tenant; multiple memberships return `TENANT_SELECTION_REQUIRED`.
- Suspended/deleted tenants and suspended memberships are excluded.
- Authenticated endpoints:
  - `GET /api/v1/tenancy/memberships`
  - `GET /api/v1/tenancy/context`
- Additive PostgreSQL migration `002_membership_context.sql` adds self-membership discovery without weakening tenant-table RLS.
- Integration SQL verifies tenant isolation, missing-context fail-closed behavior, self-membership discovery and cross-user denial.

## Deliberately not done yet
- No automatic tenant creation or ownership inference for legacy users/websites.
- No production migration or backfill.
- Legacy `Website.userId` ownership has not yet been replaced by tenant/workspace bindings.
- Website/editor routes are not yet switched to tenant authorization; that follows the reviewed backfill/binding design.
- No workspace model is created in this increment.

## Security properties
- Authentication identity comes from `requireAuth` and the persisted session.
- Tenant selector does not grant authority by itself.
- Database membership discovery is scoped by transaction-local verified user identity.
- Tenant rows remain protected by tenant RLS even while memberships are being discovered.
- Existing disconnected payment/CRM/webhook/dynamic-fetch routes remain disabled pending F04 controls.
